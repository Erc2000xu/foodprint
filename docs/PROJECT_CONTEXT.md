# 食迹 Foodprint｜项目背景与长期约束

> 建立日期：2026-07-24  
> 用途：本文件是 Foodprint 后续产品讨论、开发文档和技术迭代的共同背景。它记录长期有效的项目来源、目标与约束；具体版本进度请以 `docs/FOODPRINT_V1_1_STATUS_HANDOFF_2026-07-24.md` 及其后续交接文档为准。

## 1. 项目从哪里来

Foodprint（食迹）并非从零开始的新项目，而是从此前的开发对话和已上线 MVP 迁移而来。项目代码与历史以 GitHub 仓库为准：

- 仓库：<https://github.com/Erc2000xu/foodprint>
- 当前生产基线：V1.1.2（详见 PRODUCT.md 与 ROADMAP.md）
- 当前部署地址以受控生产别名与 Vercel 配置为准；不得在业务代码中写死某一 Vercel URL。

本文补充并固化了项目负责人的原始意图。若本文与短期需求、版本交接或代码现状冲突，应先确认哪一项是新的明确决策；不得仅凭旧文档推翻新的产品决定。

## 2. 原始产品意图

Foodprint 的起点是一个私人而可信的美食收藏与分享工具：

1. 收藏自己亲自吃过、认为很好吃、愿意推荐的餐馆；
2. 将这些真实体验组织成可回看的个人/共同餐饮地图；
3. 让朋友之间可以共享地点、体验、推荐与发现；
4. 不把它做成泛化的餐厅黄页或不受约束的 POI 爬取库。

因此，产品的核心价值是**真实体验、朋友共建、可分享的美食记忆与发现**。地点、评分、到访记录、照片和成员活动都应服务于这一目标。想去清单不等同于已到访或推荐。

## 3. 当前技术与部署事实

### 当前线上基线

在 ICP 备案完成前，网站的所有日常迭代、预览和生产发布均以 Vercel 版本为准。当前技术底座包括：

- Next.js App Router、TypeScript、Tailwind CSS；
- Supabase：认证、PostgreSQL、Storage 与 Edge Functions；
- 高德地图：地点检索、地理数据、地图/导航相关能力；
- Vercel：当前部署与发布链路。

V1.1 系列已关闭。历史交接文档只描述当时状态；当前和未来版本以 PRODUCT.md、ROADMAP.md 与已批准 Spec 为准。

### 未来正式迁移目标

项目负责人已购置中国大陆腾讯云服务器，并已购买 `foodprint.com.cn` 域名。由于 ICP 备案周期尚未结束，**现在不得将正式流量切换到该域名或腾讯云**。

待备案完成后，项目将从 Vercel 迁移/切流至腾讯云，并使用正式域名。届时的迁移不是简单替换 URL，必须按 `docs/OPERATIONS.md` 做完整验收，至少覆盖：

- TLS、DNS 和可回退的切流窗口；
- Supabase Auth Redirect URLs 与可信 Origin；
- 高德域名白名单、Key 绑定与安全密钥配置；
- 生产环境变量、PWA 路径和所有回调 URL；
- 腾讯云副本的构建、健康检查与核心用户路径验收；
- 保留 Vercel 回滚能力，直到新环境稳定。

业务代码不得写死 Vercel 地址、未来域名或某一云服务的专属实现。部署、地图、存储和认证等能力应继续通过既有 Adapter/环境变量边界保持可替换性。

## 4. 长期产品与数据约束

### 真实体验与隐私

- 新餐厅的共建应建立在成员的真实到访/真实体验之上；
- 用户精确实时位置、导航起点与私有照片访问链接不得写入共享 URL 或公开数据；
- 照片、成员数据、认证和权限必须延续现有 Supabase RLS 与服务端边界；
- 不提交密钥、数据库连接串、Service Role Key 或任何真实生产凭据。

### 高德使用边界

- 高德是地点与地理数据的权威来源；Foodprint 不维护一张不完整且容易过时的城市、商圈或地铁字典来替代它；
- 只使用高德免费版在当前主体、用途、权限和配额下明确允许的能力；不采购流量包、技术服务许可或高级服务；
- 超出免费范围、配额或许可时，必须降级、停用或改用合规方案，禁止自动付费；
- 不批量抓取、导出或再分发高德 POI、商圈、地铁等数据；缓存只能用于有限期的性能与配额控制，不能变成项目自建的权威地理库；
- Web Service Key 只能在受控服务端 Secret 中使用，绝不暴露给浏览器。V1.1 正在统一此调用边界，优先由 Supabase Edge Function 代理。

完整政策见 [`docs/AMAP_FREE_TIER_POLICY.md`](AMAP_FREE_TIER_POLICY.md)。

### 架构与变更纪律

- 业务组件不得散落直连 Supabase、高德或存储供应商的实现；优先经 `src/lib/adapters/` 定义的边界接入；
- 已在 Production 执行过的 Supabase migration 不得修改；数据库变更必须新增向前兼容的 migration；
- 重要产品改动先形成可验收的开发文档，再实施；
- 在涉及部署、数据、权限或外部服务的变更前，先确认对应环境和回滚路径。

## 6. 接下来开发时的默认判断

当需求存在多种实现时，优先选择同时满足以下条件的方案：

1. 能加强朋友间真实美食体验的收藏、分享或发现；
2. 不牺牲私密性、权限边界或数据可恢复性；
3. 不依赖高德付费能力或违规沉淀其地理数据；
4. 在当前 Vercel 阶段可稳定验证，并为备案后的腾讯云迁移保留空间；
5. 可以用明确的验收标准、测试或运行检查来确认完成。
