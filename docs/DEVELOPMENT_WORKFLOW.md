# 食迹 Foodprint｜产品开发工作流

> 生效日期：2026-07-28
> 目标：让每轮开发从想法到发布都可追溯、可验收、可恢复。

## 1. 工作流总览

```text
需求提出
  → 产品 Brief
  → 版本 Spec
  → 技术决策（必要时）
  → 实施与测试
  → 发布验收
  → 发布记录与路线图更新
```

小修复可以合并 Brief 与 Spec；涉及权限、隐私、数据迁移、第三方服务、信息架构或新用户路径的改动不得跳过 Spec。

## 2. 各阶段必须产出什么

| 阶段 | 目的 | 最小产出 | 通过条件 |
| --- | --- | --- | --- |
| Brief | 判断是否值得做 | 用户问题、目标用户、预期结果、非目标 | 项目负责人确认方向 |
| Spec | 把需求变成可实现、可验收的版本 | 范围、非范围、流程、数据/权限影响、验收标准 | 项目负责人确认范围 |
| 技术决策 | 固化重要取舍 | ADR：背景、选项、选择、后果 | 与长期约束一致 |
| 实施 | 将 Spec 落为代码 | 有边界的分支/提交、迁移、测试 | 不越过批准范围 |
| 验收 | 验证真实用户路径 | 自动化检查与角色化人工验收 | 全部关键标准通过 |
| 发布记录 | 方便下一轮接手 | 发布版本、验证、限制、回滚、待办 | 路线图状态同步 |

## 3. Spec 模板

新版本文件建议命名为 `docs/specs/YYYY-MM-version-name.md`。目录在首个新 Spec 创建时建立。

```markdown
# Foodprint｜Vx.y 名称

> 状态：草案 / 已批准 / 开发中 / 待验收 / 已关闭
> 负责人：
> 目标发布日期：仅在确认后填写

## 背景与用户问题
## 目标与成功判断
## 范围
## 非范围
## 用户流程与界面规则
## 数据、权限、隐私与第三方影响
## 技术方案与迁移/回滚
## 验收标准
## 发布检查
## 未决问题与后续事项
```

## 4. 决策记录（ADR）何时需要

出现以下任一情况时，在 `docs/decisions/` 新增 ADR；无需为普通文案、样式或局部 Bug 修复创建。

- 新增或替换 Supabase、高德、存储、部署等第三方能力；
- 改变权限、隐私、数据保留、导出或定位策略；
- 新增数据库核心模型或不可逆迁移风险；
- 改变产品信息架构或已定长期原则；
- 在多个可行方案中做了会长期影响维护成本的选择。

ADR 应记录：背景、候选方案、最终选择、理由、代价、复核条件与日期。

## 5. 开发与发布纪律

1. 开始编码前，先把当前版本在 `ROADMAP.md` 标为“开发中”，并链接 Spec。
2. 代码、migration、测试和文档应在同一版本中交付；已上线 migration 不修改，只新增。
3. 每次提交前至少执行类型检查、Lint、测试和生产构建；按改动风险补充测试。
4. 权限相关功能至少以 Owner、Admin、Member 三种角色人工验收。
5. 部署、密钥、地图、认证或数据导出改动必须同时写清配置、监控和回滚路径。
6. 验收未通过时，版本保持“待验收”；不得因为代码已合入就标记完成。
7. 发布关闭后，把未做事项移入路线图或明确的运维待办，不留在旧版本的“未完成”状态。

## 6. 轻量优先级规则

- **P0**：安全、数据正确性、登录/邀请、核心记录与生产可用性。
- **P1**：主要发现路径、地图体验、地点质量和小组运营效率。
- **P2**：体验增强、视觉完善、非核心自动化。
- **候选**：尚未由真实使用或明确目标证明价值的想法。

优先解决已验证的用户问题和 P0 风险；路线图中的远期方向不会自动获得开发优先级。

## 7. GitHub 分支、Preview 与版本

三者不是同一个概念：

| 概念 | 它是什么 | Foodprint 的规则 |
| --- | --- | --- |
| `main` | 唯一的正式代码主线 | 只保留已审核、可发布的内容；推送/合入后触发 Vercel Production |
| `codex/<工作范围>` 分支 | 为一项明确工作隔离出的临时开发线 | 例如 `codex/v1-2-home-discovery`；它不是产品版本，也不等于已上线 |
| Preview | Vercel 为分支或 PR 自动生成的测试站点 | 用于先验收真实界面与流程；不是正式生产版本 |
| 产品版本 | 对用户有意义的一组已发布能力 | 以 Spec、发布记录与 `ROADMAP.md` 为准，而非以分支名判断 |

### 标准生命周期

```text
从最新 main 创建一个工作分支
  → 在分支实现一个已批准的 Spec 或修复任务
  → Preview 测试与人工验收
  → 创建 PR，审核变更范围
  → 合入 main，触发 Production
  → 生产验收与发布记录
  → 删除已合入的远端工作分支
```

- 每个分支只服务一个清楚的工作范围；普通修复可用 `codex/fix-<问题>`，版本能力可用 `codex/v1-2-<主题>`。
- 不再把每次临时试验都长期保留为远端分支。分支合入 `main` 且确认生产稳定后，应删除该远端分支；Git 的提交历史和发布文档仍会保留。
- 除紧急线上修复且项目负责人明确同意外，不直接向 `main` 推送开发中的代码；先经 Preview 和 PR。
- 删除分支只删除一个“指向提交的标签”，不等于删除已合入 `main` 的功能；但任何未被 `main` 包含的旧分支，必须先比较、备份并经项目负责人确认，不能凭名称直接删除。
