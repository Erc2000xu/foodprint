# 食迹 Foodprint｜产品开发工作流

> 生效日期：2026-07-28
> 目标：让每轮开发从想法到发布都可追溯、可验收、可恢复。

## 1. 三方角色与决策边界

Foodprint 采用“项目负责人 + ChatGPT + Codex”的协作模式。它不是把产品和技术割裂的单向流水线，而是在每个关键决策点形成短反馈闭环。

| 角色 | 主要责任 | 不应替代谁做决定 |
| --- | --- | --- |
| 项目负责人（你） | 定义真实问题、目标用户、优先级、取舍、可接受成本与最终验收；批准 Spec、发布和重大变更 | 不需要独自把自然语言翻译成技术方案或项目计划 |
| ChatGPT（产品协作） | 把你的想法梳理成 Brief、路线图、里程碑、用户流程、Spec 和验收口径；提出产品取舍与待决问题 | 不替项目负责人批准范围、上线或隐私/商业取舍；不替 Codex 保证实现可行性 |
| Codex（工程交付） | 阅读现状、评估技术可行性与风险、提出实现计划；编码、测试、部署检查、发布记录和维护 | 不在需求不清楚时自行扩张产品范围；不替项目负责人决定产品优先级或重大体验取舍 |

### 核心规则

1. **你是唯一的产品与发布决策者。** ChatGPT 和 Codex 都可以提出建议、指出风险，但不把建议当作已批准需求。
2. **ChatGPT 产出“要做什么、为什么做、如何判断成功”。** 它特别适合把连续对话收束为可讨论的产品材料。
3. **Codex 产出“能否安全地做、怎样做、是否已做到”。** 它必须在权限、数据、地图、第三方服务、迁移或成本风险较高时，先反馈技术边界。
4. **Spec 不是一次性单向交接。** 对重大功能，ChatGPT 先起草，Codex 做可行性预检，你再批准最终范围；这样能避免文档理想化或实现反向改变产品意图。
5. **实际使用反馈优先于假设。** 你体验后提出的问题，先由 ChatGPT/Codex 帮助归类为 Bug、体验优化、版本需求或延期运维，再决定进入哪个版本。

## 2. 工作流总览

```text
你用自然语言提出问题或目标
  → ChatGPT 起草产品 Brief
  → Codex 可行性预检（重大改动必需）
  → ChatGPT 完善版本 Spec
  → 你批准范围与优先级
  → Codex 实施与测试
  → 你进行真实体验验收
  → Codex 发布记录，ChatGPT/你更新路线图
```

小修复可以合并 Brief 与 Spec；涉及权限、隐私、数据迁移、第三方服务、信息架构或新用户路径的改动不得跳过 Spec。

## 3. 各阶段必须产出什么

| 阶段 | 主责角色 | 目的 | 最小产出 | 通过条件 |
| --- | --- | --- | --- | --- |
| Brief | ChatGPT + 项目负责人 | 判断是否值得做 | 用户问题、目标用户、预期结果、非目标 | 你确认方向 |
| 可行性预检 | Codex | 提前暴露数据、权限、成本、迁移与第三方风险 | 实现选项、风险、估时量级、待决问题 | 重大风险已有处理决定 |
| Spec | ChatGPT 起草，项目负责人批准，Codex 复核 | 把需求变成可实现、可验收的版本 | 范围、非范围、流程、数据/权限影响、验收标准 | 你确认范围 |
| 技术决策 | Codex 起草，项目负责人确认 | 固化重要取舍 | ADR：背景、选项、选择、后果 | 与长期约束一致 |
| 实施 | Codex | 将 Spec 落为代码 | 有边界的分支/提交、migration、测试 | 不越过批准范围 |
| 验收 | 项目负责人 + Codex | 验证真实用户路径 | 自动化检查与角色化人工验收 | 全部关键标准通过，或明确保留体验观察入口 |
| 发布记录 | Codex；ChatGPT/项目负责人复核产品状态 | 方便下一轮接手 | 发布版本、验证、限制、回滚、待办 | 路线图状态同步 |

## 4. Spec 模板

新版本文件建议命名为 `docs/specs/YYYY-MM-version-name.md`。目录在首个新 Spec 创建时建立。

```markdown
# Foodprint｜Vx.y 名称

> 状态：草案 / 已批准 / 开发中 / 待验收 / 已关闭
> 负责人：
> 目标发布日期：仅在确认后填写

## 背景与用户问题
## 目标与成功判断
## 范围
## 非范围
## 用户流程与界面规则
## 数据、权限、隐私与第三方影响
## 技术方案与迁移/回滚
## 验收标准
## 发布检查
## 未决问题与后续事项
```

## 5. 决策记录（ADR）何时需要

出现以下任一情况时，在 `docs/decisions/` 新增 ADR；无需为普通文案、样式或局部 Bug 修复创建。

- 新增或替换 Supabase、高德、存储、部署等第三方能力；
- 改变权限、隐私、数据保留、导出或定位策略；
- 新增数据库核心模型或不可逆迁移风险；
- 改变产品信息架构或已定长期原则；
- 在多个可行方案中做了会长期影响维护成本的选择。

ADR 应记录：背景、候选方案、最终选择、理由、代价、复核条件与日期。

## 6. 开发与发布纪律

1. 开始编码前，先把当前版本在 `ROADMAP.md` 标为“开发中”，并链接 Spec。
2. 代码、migration、测试和文档应在同一版本中交付；已上线 migration 不修改，只新增。
3. 每次提交前至少执行类型检查、Lint、测试和生产构建；按改动风险补充测试。
4. 权限相关功能至少以 Owner、Admin、Member 三种角色人工验收。
5. 部署、密钥、地图、认证或数据导出改动必须同时写清配置、监控和回滚路径；数据库与 Vercel 发布必须遵循 [免费版发布与数据库迁移 SOP](RELEASE_SOP.md)，不能在本机或 SQL Editor 临时绕过。
6. 验收未通过时，版本保持“待验收”；不得因为代码已合入就标记完成。
7. 发布关闭后，把未做事项移入路线图或明确的运维待办，不留在旧版本的“未完成”状态。

## 7. 轻量优先级规则

- **P0**：安全、数据正确性、登录/邀请、核心记录与生产可用性。
- **P1**：主要发现路径、地图体验、地点质量和小组运营效率。
- **P2**：体验增强、视觉完善、非核心自动化。
- **候选**：尚未由真实使用或明确目标证明价值的想法。

优先解决已验证的用户问题和 P0 风险；路线图中的远期方向不会自动获得开发优先级。

## 8. GitHub 分支、PR、生产发布与版本

四者不是同一个概念：

| 概念 | 它是什么 | Foodprint 的规则 |
| --- | --- | --- |
| `main` | 唯一的正式生产代码主线 | 只接收通过 PR CI 的内容；合入本身不部署，负责人手动启动发布 workflow 后才更新 Supabase 并触发 Vercel Production |
| `codex/<工作范围>` 分支 | 为一项明确工作隔离出的临时开发线 | 例如 `codex/v1-2-home-discovery`；它不是产品版本，也不等于已上线 |
| PR CI | GitHub 临时验证环境 | 用干净 Supabase 容器重放全部 migration，不读取生产凭据或真实数据 |
| Production Deploy Hook | 数据库成功更新后才触发的 Vercel 构建 | 单生产方案下不让任意 Preview 连接 production Supabase |
| 产品版本 | 对用户有意义的一组已发布能力 | 以 Spec、发布记录与 `ROADMAP.md` 为准，而非以分支名判断 |

### 标准生命周期

~~~text
从最新 main 创建一个工作分支
  → 在分支实现一个已批准的 Spec 或修复任务
  → 创建 PR 到 main，审核范围并通过应用 / migration CI
  → 项目负责人合入 main；此时没有云端副作用
  → 项目负责人手动运行 Release production 并输入确认词
  → GitHub Actions 先更新 production Supabase，再触发 Vercel Production
  → 生产验收与发布记录
  → 删除已合入的远端工作分支
~~~

- 每个分支只服务一个清楚的工作范围；普通修复可用 `codex/fix-<问题>`，版本能力可用 `codex/v1-2-<主题>`。
- 工作分支不是永久分支。分支已合入 main 且确认生产稳定后，应删除该远端工作分支；Git 的提交历史和发布文档仍会保留。
- 除紧急线上修复且项目负责人明确同意外，不直接向 `main` 推送开发中的代码；先经 PR、CI 和对应验收。
- 迁移、Edge Function 与 Vercel 的准确执行顺序、凭据边界、单生产限制和失败动作以 [RELEASE_SOP.md](RELEASE_SOP.md) 为准。
- 删除分支只删除一个“指向提交的标签”，不等于删除已合入 `main` 的功能；但任何未被 `main` 包含的旧分支，必须先比较、备份并经项目负责人确认，不能凭名称直接删除。

## 9. 阶段产物、存放位置与交接

聊天用于讨论，GitHub 仓库用于保存可追溯的项目事实；本地电脑用于实施和临时验证。任何重要结论不能只停留在聊天记录或某一台电脑上。

| 阶段 | 主要产物 | 主存放位置 | 交接给谁 |
| --- | --- | --- | --- |
| 产品讨论 | 对话、问题清单、备选方向 | ChatGPT 对话；确认后提炼到 GitHub 文档 | ChatGPT → 项目负责人 |
| 长期方向 | 产品定位、路线图、版本状态 | `docs/PRODUCT.md`、`docs/ROADMAP.md`，提交到 GitHub | 项目负责人 / ChatGPT → Codex |
| 单版本立项 | Brief、Spec、原型/截图链接、验收标准 | `docs/specs/`，提交到 GitHub | ChatGPT / 项目负责人 → Codex |
| 技术取舍 | ADR、实现计划、风险与迁移方案 | `docs/decisions/` 或 Spec 的技术章节，提交到 GitHub | Codex → 项目负责人 / ChatGPT |
| 实施 | 代码、测试、数据库 migration、分支与 PR | 本地开发后提交到 GitHub 工作分支 | Codex → 项目负责人 |
| 测试与体验 | 自动化检查、Preview、人工验收结果、复现步骤 | PR、发布记录；必要时在 Spec 更新状态 | Codex + 项目负责人 |
| 发布与维护 | 发布记录、已知限制、回滚与后续事项 | `docs/releases/` 或版本交接文档，提交到 GitHub | Codex → 下一轮协作 |

### 本地、GitHub 与第三方平台的边界

- **本地电脑**：代码编辑、临时文件、调试输出和尚未提交的草稿；它不是长期唯一存档。
- **GitHub**：代码、批准后的 Markdown 文档、测试、PR 和发布历史的唯一协作事实来源。只要一个结论会影响后续开发，就应进入 GitHub。
- **Vercel / Supabase / 高德控制台**：部署、数据库、密钥、配额和运行状态；不把密钥、生产数据或控制台截图中的敏感信息提交到 GitHub。
- **ChatGPT 对话**：适合探索和起草；被批准的 Brief / Spec 由 Codex 写入 GitHub，避免“聊天里有决定、仓库里没有”的断层。

### 每次交接的最小交接包

无论是 ChatGPT 交给 Codex、Codex 交给你，还是下一位 Codex 接手，都应给出以下六项：

1. 当前目标与用户问题；
2. 对应的 GitHub 文档、分支和 PR 链接；
3. 已批准范围与明确非范围；
4. 当前状态：草案 / 开发中 / 待验收 / 已发布 / 体验观察中；
5. 已完成的检查、Preview 或人工验收结果；
6. 未决问题、风险和“下一步唯一动作”。

## 10. 一条工作分支为默认，不把并行变成混乱

对于 Foodprint 当前规模，默认同时只做**一个**产品工作分支：长期 `main` 加一条正在进行的 `codex/<工作范围>` 分支。这是最容易管理、也适合当前免费版单生产发布方式。

但分支数量可以暂时大于一，前提是每条都有明确状态和所有者：

| 情况 | 是否允许额外分支 | 规则 |
| --- | --- | --- |
| 正常迭代 | 不需要 | 完成、合入、删除后才开始下一项 |
| 紧急线上修复 | 允许 | 从最新 `main` 开 `codex/fix-<问题>`；修复合入 main 后，其他工作分支先同步最新 main 再继续 |
| 明确需要并行的独立任务 | 经项目负责人确认后允许 | 每条分支都从同一最新 `main` 创建，各自有 Spec、PR 和验收范围 |
| 开发到 80% 后暂缓 | 允许，但必须显式“暂停” | 提交可恢复的 WIP，Draft PR/路线图标注原因、剩余工作与恢复条件；不悄悄遗留 |

并行分支天然不会立即互相覆盖，因为它们各自是独立的提交历史；真正的冲突发生在第二条分支准备合入 main 时，且两者修改了同一段文件、数据模型或迁移顺序。处理规则是：

~~~text
分支 A 先合入 main
  → 分支 B 拉取最新 main 并重新测试
  → 如有冲突，由 Codex 解决并说明取舍
  → 再合入 main
  → 每次生产发布都由项目负责人单独手动确认
~~~

因此，长期规则不是“永远只能有一个分支”，而是：**默认一个活跃分支；只有在收益明确时才并行；每条并行分支必须可识别、可恢复、可关闭。** 对数据库 migration、权限和共享用户路径的并行改动尤其谨慎，优先串行处理。
