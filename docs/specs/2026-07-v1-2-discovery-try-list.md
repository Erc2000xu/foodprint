# V1.2｜发现与去试试

> 状态：待批准
> 前置依赖：P0 高德连接可靠性与安全基线已验收
> 目标：明确已推荐地点与待验证候选地点的边界，让用户能轻量记录“想试”，并以一次真实体验完成流转。

## 1. 用户问题

当前入口名称与内容不匹配：首个页面实际承担找店和发现职责；“想去”既像收藏又像待验证地点，语义混淆；地点一旦添加即上架，缺少“先试后推荐”的路径。

## 2. 目标与非目标

### 目标

- 将主入口命名为“发现”，只展示小组内真实推荐的地点。
- 新增“去试试”，承接来自朋友、短视频、社交媒体或口口相传的候选地点。
- 用最少字段完成加入和验证，避免把候选清单做成复杂待办。
- 保留“下回吃”作为个人对已推荐地点的收藏，不与候选逻辑混用。

### 非目标

- 不建立公开差评库、避雷榜、商家申诉或用户互动评论系统。
- 不在本版本实现重复到访、到访时间线、三级小碗或地点详情大改版。
- 不允许用户手填并永久沉淀未经高德确认的大量 POI；地点必须先由高德检索确认。

## 3. 信息架构与页面

| 位置 | V1.2 行为 |
| --- | --- |
| 发现 | 原“地图”入口改名。列表仍为首要形态，展示仅限已推荐地点；地图切换保留现有能力/占位，不承诺动态地图。 |
| 去试试 | 新一级入口。顶部是明显的小 Banner/Bar：大号加号与轻量引导；下方是候选地点卡片列表。 |
| 记一顿 | 仍是已推荐地点真实标记的入口；候选验证会在 V1.3 完整改造，本版本提供最小可行的“我去试过了”流转入口。 |
| 下回吃 | 个人收藏清单，只允许收藏发现中的已推荐地点。 |

## 4. 用户流程

### 4.1 加入去试试

1. 用户进入“去试试”，点击顶部加号区域。
2. 搜索并选择高德地点，确认名称和地址。
3. 可选填写两项：从哪里听说的；为什么想试/一句自己的期待。
4. 提交后回到列表，卡片立即出现。

候选卡只显示地点名称、行政区/地址、用户的一句原话、加入人和轻量操作；不要求照片、菜品、评分或长备注。

### 4.2 真实体验后的流转

1. 用户在候选卡点击“我去试过了”。
2. 首先回答：这家值得推荐吗？
3. 若是：完成最小真实到访记录，候选从去试试移除，地点进入发现。
4. 若否：确认后候选从去试试移除，不进入发现；仅保留小组内最小化后台验证记录用于去重和避免反复加入。

不值得推荐的记录不在发现、饭后聊、搜索结果或他人候选卡中以公开负面内容呈现。后续有人再次尝试同一地点时，系统可提示“这家已经有人试过”，但具体提示文案、可见范围和是否允许重新加入需在实施前由负责人确认。

## 5. 数据与权限设计

### 5.1 建议模型

- place：跨小组的规范地点主实体，来自确认后的高德 POI；不等于公开可浏览的餐厅库。
- group_place：小组已推荐地点。发现只查询该实体。
- place_candidate：小组候选关系，状态为 pending、promoted、dismissed。
- candidate_note：可选来源和短句；不作为公开评价内容。

唯一性建议：同一 group_id + place_id 同时只能有一条 pending 候选。promoted 后复用同一 group_place；dismissed 不在前台列表显示。完整结构、RLS 与迁移路线以地点生命周期 ADR 的工程设计为准。

### 5.2 权限与隐私

- 仅有效小组成员可看见本小组 pending 候选、创建候选和发起到访验证。
- 创建者可编辑/删除自己尚未验证的候选；管理员的治理能力沿用现有角色，需明确审计规则后再开放。
- dismissed 状态和可选原因不得通过客户端任意查询暴露给非授权成员。
- 搜索只实时调用高德；不将用户搜索历史、精确地址和来源文本用于广告或跨小组推荐。

## 6. 技术实施顺序

1. P0 验收：高德搜索稳定、来源校验通过。
2. 提交 ADR 确认的数据模型和生命周期状态机。
3. 新增向前兼容 Supabase migration、索引、RLS 和 RPC/adapter；不改已上线 migration。
4. 实现去试试列表、顶部加号入口、POI 搜索确认和可选短表单。
5. 实现候选的去重、验证、promoted/dismissed 流转，以及发现/下回吃的过滤边界。
6. 完成空状态、网络/高德失败状态、小组/角色验收和数据迁移演练。

## 7. 验收标准

- 发现底部导航和标题均使用“发现”，且没有候选地点混入。
- 去试试顶部可见轻量加号入口；加入一间餐厅只需选择高德 POI，两个文字字段均为选填。
- 候选卡不展示照片、评分或冗长表单字段。
- 候选验证为推荐后，恰好生成/复用一个小组推荐地点，并从候选列表移除。
- 候选验证为不推荐后，不出现在发现、下回吃、饭后聊或普通搜索结果；后台保留受权限保护的状态记录。
- 同一小组中重复加入 pending 候选有清晰提示，不产生双卡片。
- 不同小组的数据完全隔离；Member、Admin、Owner 的权限均经过人工验收。
- 类型、Lint、测试、构建、移动端手工验收和 migration 回滚演练全部通过。

## 8. 风险、回滚与未决项

- 风险：候选与推荐地点创建并发导致重复。缓解：数据库唯一约束与事务化 RPC。
- 风险：去试试被误解为公开避雷。缓解：只展示候选和正向发现，隐藏 dismissed 负面详情。
- 回滚：隐藏新入口并回退应用；保留新增数据表/RLS，不删除已产生记录，后续以前向 migration 修复。
- 未决：候选的来源是否提供预设项；再次遇到已 dismissed 的地点时的最终提示与重试政策；管理员是否可代为处理候选。
