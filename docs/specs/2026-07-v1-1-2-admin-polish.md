# 食迹 Foodprint｜V1.1.2 管理页体验修复

> 状态：已关闭；项目负责人已完成 Preview 人工验收
> 类型：V1.1.1 发布后的体验优化补丁
> 记录日期：2026-07-28
> 依据：项目负责人在 V1.1.1 Preview 的 Owner 管理页实际体验反馈

## 1. 背景与目标

V1.1.1 已具备成员角色、状态和邀请治理能力，但当前移动端成员卡片存在角色用语不一致、邮箱被管理操作挤压、注册流程对 Owner 不够清楚的问题；数据导出的位置也不符合其低频使用属性。

本补丁只优化 Owner/Admin 管理页的文案、信息层级和布局，不改变已有角色权限、邀请安全模型、认证机制或数据库结构。

## 2. 范围

### 2.1 统一成员角色用语与成员卡片

1. 所有角色展示统一使用英文、首字母大写的 `Owner`、`Admin`、`Member`；不得再出现“成员”和 `member` 混用的角色标签或下拉选项。
2. “成员”区块的简述改为清楚的角色说明，建议文案：

   > 角色说明：`Owner` 可管理成员角色、状态和全组导出；`Admin` 可管理邀请并查看成员目录；`Member` 可记录和浏览共同地图，不能查看成员目录或邮箱。

3. 在 420px 移动端宽度，成员卡片改为“身份信息在上、管理操作在下”的两层布局：

   ```text
   头像  昵称
         完整邮箱地址
         Owner / Admin / Member · Active

         [角色选择] [更新角色] [暂停或恢复]
   ```

4. 邮箱必须完整可读，可换行但不能被按钮压缩、遮挡或省略。角色选择、更新角色和暂停/恢复操作不得与邮箱抢占同一水平空间。
5. Owner 本人仍不可被改角色或暂停；非 Owner 的角色/状态操作保持 V1.1.1 当前权限规则。

### 2.2 在成员区块说明新用户注册流程

在成员角色说明下方加入 1–4 的简要流程图/步骤卡片，文案应准确反映当前系统：

1. **分享邀请**：Owner 或 Admin 创建有效邀请链接，并私下发送给朋友。
2. **创建账号**：朋友打开链接，填写昵称、邮箱和至少 8 位密码。
3. **验证邮箱**：朋友打开验证邮件中的链接；系统验证账号并返回原邀请。
4. **自动加入**：验证成功后系统自动完成入组并进入食迹；之后再次使用时，可用该邮箱和密码登录。

说明：当前代码在邮箱验证成功后会自动回到邀请链接并完成入组，用户无需在“成功”页再次手动登录。此处不调整 Supabase 邮箱确认配置、SMTP、邮件模板或认证逻辑。

### 2.3 将数据导出移至管理页底部

将“导出我的数据”区块移动到 Owner/Admin 管理页内容的最后一张卡片，即成员区块之后；不改变下载接口、审计记录和现有导出内容。

**已确认的权限边界：** 当前实现允许每位已登录成员导出自己的数据，只有 Owner 能导出整个共同地图。本补丁只调整位置，不改变这项权限；整张数据导出卡片不因本补丁而限制为 Owner 专属。

## 3. 非范围

- 不接入 SMTP、改动验证邮件或关闭邮箱确认；
- 不改变 Owner / Admin / Member 的数据库权限、RLS、RPC 或审计；
- 不增加 Owner 转移、多 Owner 或自定义角色；
- 不改变邀请有效期、使用次数、加密保存或历史保留策略；
- 不修改数据导出 JSON 格式或照片存储策略。

## 4. 技术验证要点

预计只涉及管理页组件、成员角色控件和移动端样式：

- `src/app/admin/page.tsx`
- `src/components/admin/member-role-control.tsx`
- `src/components/admin/member-status-button.tsx`（如为统一操作布局而需要）
- `src/components/admin/data-export-panel.tsx`
- `src/app/globals.css`

不预期需要新增 migration、修改 Supabase RPC 或更改认证回调。Codex 实施前应确认移动端卡片布局不会影响 Owner/Admin/Member 的可见性与操作权限。

## 5. 验收标准

1. Owner 管理页、成员卡片和角色下拉中，角色只显示 `Owner`、`Admin`、`Member`，不再出现中文角色名或小写原始值。
2. 在 420px 宽度，任一成员的完整邮箱都可读；管理操作位于邮箱下方，按钮不会覆盖或压缩邮箱。
3. Owner 可继续把活跃非 Owner 成员在 `Admin` 与 `Member` 间切换，并暂停/恢复；Admin 和 Member 的原有限制不回归。
4. 成员区块显示 1–4 注册流程，准确说明“邮箱验证后自动入组；以后使用邮箱和密码登录”。
5. 数据导出卡片位于管理页最后；除项目负责人另行批准外，维持“所有成员可导出个人数据、仅 Owner 可导出全组”的现有规则。
6. Owner、Admin、Member 分别在 Preview 中完成成员页回归；新增一张 420px 成员管理截图作为验收记录。

## 6. 与 V1.1.1 的收尾关系

V1.1.2 是 V1.1.1 的体验收尾补丁。Codex 实施时除本 Spec 的验收标准外，还必须回归 V1.1.1 的邀请创建/撤销、成员目录隐私、Owner/Admin/Member 权限、地点搜索、标记、想去与全组导出。项目负责人完成实际体验验收后，V1.1.1 和 V1.1.2 才一起标记为“已关闭”。

## 7. 实施前剩余的展示决定

角色旁的状态统一使用 `Active` / `Suspended`。这与 `Owner` / `Admin` / `Member` 的首字母大写展示规则一致，同时不改变数据库内的原始状态值。

## 8. 实施前技术验证

2026-07-28 已确认本补丁只涉及管理页服务器组件、现有角色控件和 CSS 布局：`update_member_status`、`set_member_role` 与既有 RLS/RPC 不需要改动。管理权限继续由服务端 RPC 强制执行；本次仅把移动端成员卡片改为身份信息在上、操作在下，避免邮箱与按钮争抢同一行。无需新增 migration、认证回调或部署配置。
