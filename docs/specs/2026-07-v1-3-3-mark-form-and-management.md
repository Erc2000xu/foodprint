# V1.3.3｜记一顿表单、四维图标与地点内容管理

> 状态：完整开发稿，待产品负责人批准进入开发
> 前置版本：V1.3.1 已完成开发、待 Preview 验收；V1.3.2 产品需求已确认、尚未开发
> 本轮边界：优化记一顿表单及全局四维图标，补齐 Owner/Admin 的地点、候选与到访内容管理；不实施 V3 整体视觉改版

## 1. 当前问题

1. “必填”在标题、图例和确认项中重复出现，颜色和位置不一致，反而削弱了字段层级。
2. 多个字段使用完整边框和浅色底，legend、选项文字和边框相互挤压，窄屏下容易产生文字越界或视觉粘连。
3. “首次收录必须是你愿意推荐给朋友的地点”出现在表单中段，用户填写一部分后才看到最重要的准入规则。
4. 三级推荐虽然已经使用统一小碗资产，但没有解释三个等级的判断差异。
5. “吃得香 / 坐得住 / 聊得开 / 花得值”对产品制定者清楚，对第一次使用的成员不够自解释。
6. 地点大类中的“小吃 / 街头餐饮”与菜系层级重复。
7. 上传照片没有说明首页按竖向比例展示，用户上传横图后可能对居中裁切结果产生误解。

## 2. 本轮目标

- 用户在开始填写前，先知道这条记录必须来自亲自体验且愿意推荐。
- 用户不需要猜“值得去 / 想再去 / 会专门去”的差别。
- 用户不需要记忆四个体验维度的产品定义。
- 页面只在必要位置出现边框和底色，320px 宽度下不出现文字、legend 或选项越界。
- 必填规则明确但不制造红色警告噪音。
- 本轮只提升现有视觉系统内的清晰度，不更换品牌皮肤、字体体系或导航结构。

## 3. 建议的信息结构

页面方向采用 C“先选择，再补充”：在真实推荐确认之后，先完成推荐强度和“好在哪儿”，再补到访日期、地点类型、菜系与可选内容。保持连续单页，不引入真正的分步提交。

### 3.1 先确认这家店

顺序：

1. 返回重新搜索。
2. 地点名称与地址。
3. 真实推荐确认。
4. 到访日期。
5. 地点类型。
6. 主菜系。

新地点确认文案：

> 这是我亲自去过、也愿意推荐给朋友的地方
> 首次收录只接受真实、正向的推荐。

该确认项移到地点信息之后、所有输入之前。表单内容保持可见；未确认时不隐藏字段，但不能提交。

### 3.2 说说为什么推荐

包含推荐强度和“好在哪儿”。

推荐强度的固定解释：

| 等级 | 名称 | 简短解释 |
| --- | --- | --- |
| 1 | 值得去 | 在附近，会放心推荐 |
| 2 | 想再去 | 吃过还惦记，愿意再来 |
| 3 | 会专门去 | 值得特意安排一趟 |

每个选项显示一枚对应 `BowlIcon`、名称和一行解释。整张选择卡都可点击，选中状态同时使用边框、浅底色和选中标记，不只依靠颜色。

#### 三级推荐资产的强制复用规则

- 页面意向图中由生成工具自动绘制的小碗只用于表达布局，**不得进入开发或资产目录**。
- 前端必须调用现有 `BowlIcon` 组件；组件继续映射以下已确认文件：
  - `public/icons/recommendation/bowl-level-1-ui.png`
  - `public/icons/recommendation/bowl-level-2-ui.png`
  - `public/icons/recommendation/bowl-level-3-ui.png`
- 页面组件不得复制图片路径、另存意向图小碗、使用 emoji、星级或临时 SVG 替代。
- 数据库、RPC 和服务端接口只保存或返回 `1 / 2 / 3` 推荐等级，不保存前端图片路径。前端统一用等级调用 `BowlIcon`，确保以后替换资产时不需要迁移业务数据。
- 开发验收时必须逐页核对发现、地图、地点详情、记一顿和饭后聊使用的是同一组件与同一组图片。

“好在哪儿”的固定解释：

| 内部值 | 名称 | 解释 | 图标语义 |
| --- | --- | --- | --- |
| `tasty` | 吃得香 | 味道和出品让人满意 | 餐具 |
| `comfortable` | 坐得住 | 环境舒服，愿意多待一会 | 椅子 |
| `good_for_chat` | 聊得开 | 适合一起吃饭聊天 | 对话气泡 |
| `good_value` | 花得值 | 价格与体验相称 | 硬币 |

四项以 2 × 2 选择卡呈现；320px 下仍保留两列，但文字说明允许两行。每次至少选择 1 项、最多 4 项，并显示 `已选 0/4`。四项可同时选择；取消任一项后即时更新计数。

四枚图标必须与发现首页复用同一资产和组件。意向稿中的图标仅表示语义，不直接作为上线资产。

图标方案确认后的工程规则：

- 数据层继续保存 `tasty / comfortable / good_for_chat / good_value`，不保存图标名称或文件路径。
- 前端建立唯一的 `GoodAtIcon` 映射组件，由语义 slug 选择 `public/icons/good-at/*-ui.png`。
- 记一顿、发现卡、地点详情和饭后聊只能调用该组件，不能在各页面分别画图标。
- 产品负责人于 2026-07-30 确认 D“温暖餐桌物件”为正式方向。正式资产采用 1254px 透明 PNG 母稿和 256px 透明 PNG 程序版；不直接加载母稿，不从方向板裁切，也不自动矢量化。
- 图标容器使用 `object-fit: contain`；记一顿选择卡目标显示 56px、320px 窄屏不得小于 48px；发现卡不得小于 28px，推荐使用 32px；地点详情建议 36px；饭后聊不得小于 28px。
- 默认图标不额外套圆形或方形徽章，避免与三级小碗奖章混淆。
- 选中态使用浅鼠尾草底、深青边框、原生勾选状态或明确选中文字；不得使用深青实心底，因为椅架会失去对比度。
- 必须在 24、28、32、48、56px 下检查清晰度；图标始终配中文名称，不单独承担完整含义。

五套图标方向稿与比较结论保存在 `docs/design/v1-3-3-good-at-icons/`。方向稿只用于确定语义、线条、容器和色彩，不得直接裁切为上线资产或自动矢量化后提交。

#### IC-02 的全局接入范围

V1.3.3 开发时，凡界面展示四维评价，均必须使用同一 `GoodAtIcon`：

1. 记一顿首次添加地点的 2 × 2 选择卡。
2. 已有地点再次到访且选择“有变化”时的四维编辑。
3. 发现页地点卡的四维人数汇总。
4. 地点详情头部汇总、当前观点和到访记录快照。
5. 饭后聊中的到访记录卡。
6. 后续新增的地图详情、个人记录或汇总页面；不得新画同义图标。

服务端只返回 slug 和人数等业务数据；图片路径映射只存在于前端统一组件中。

### 3.3 留下这顿

顺序：

1. 推荐菜 / 饮品。
2. 饭后感受。
3. 照片。
4. 匿名分享给小组。
5. 提交按钮。

推荐菜和感受继续为可选项，不因为视觉分组变成必填。

匿名说明沿用既有治理口径：

> 大家会看到“匿名成员”；你自己仍可管理和导出这条记录。

## 4. 必填表达

- 页面只在首个输入区上方解释一次：`带 · 的项目需要填写`。
- 必填字段标题右侧只显示小型品牌橙色圆点，不再重复显示红色“必填”。
- 不能只靠颜色表达：HTML 保留 `required`、`aria-required` 和明确的字段级错误文字。
- 提交失败后，页面把焦点移动到第一个未完成字段，并显示具体原因，例如“请选择这次的推荐强度”，不使用笼统的“请完成必填项”。
- 可选项继续显示一次低对比度“可选”，但同一分组内可在分组标题统一说明，避免每行重复。

必填项为：

- 真实推荐确认；
- 到访日期；
- 地点类型；
- 主菜系；
- 推荐强度；
- “好在哪儿”1–2 项。

## 6. 照片上传提示

上传区固定显示：

> 首页按 3:4（宽:高）竖图展示，建议优先上传竖版照片；横图会居中裁切。
> 最多 9 张 · 上传前压缩并移除拍摄信息。

说明中的比例必须写成 `3:4（宽:高）`，避免把“竖版 4:3”误读成宽大于高。

本轮不新增手动裁切、封面选择或焦点位置编辑。预览缩略图使用与首页相同的 3:4 框，尽量让用户在上传阶段预见实际裁切结果；原图仍按既有策略压缩保存。

## 7. 图片上传与中国大陆合规判断

本节是产品与工程风险清单，不构成法律意见。大陆正式发布前仍需由实际运营主体、接入商和合格顾问按当时规则确认。

### 7.1 备案结论

- 允许上传照片本身不会单独把网站从“备案”变成另一类许可，也不是是否需要 ICP 备案的判断开关。
- 若在中国大陆境内提供非经营性互联网信息服务，原则上按实际服务项目履行 ICP 备案；若构成经营性互联网信息服务或涉及需前置审批的特定服务，则需要另行判断许可。
- 如果未来发布为原生 App、小程序或进入应用分发渠道，还需按具体载体核对 App 备案、平台审核和相关信息服务规则；当前网页/PWA 与原生 App 不能直接视为同一种备案对象。
- 境外托管不等于可以忽略面向中国大陆用户时适用的个人信息、内容与数据义务，也不能用“已备案”替代其他合规工作。

### 7.2 照片功能新增的主要义务

1. **内容治理**：成员可上传文字和图片后，运营方需要有用户规则、违法违规内容处置、投诉/举报或联系渠道、管理员最小化处理流程和处置记录。小组私密会降低传播范围，但不会自动消除内容管理责任。
2. **账号真实性**：若产品被认定为向用户提供信息发布服务，正式大陆运营时需要专项核对真实身份认证要求。当前仅邮箱注册不应在未经确认时被写成“已经满足”。
3. **个人信息与肖像**：照片可能包含可识别的人脸、位置、桌牌、车牌或其他个人信息。隐私政策应说明收集目的、可见范围、存储位置、保存期限、删除/导出和投诉方式；上传规则应要求用户有权上传并尊重他人肖像、隐私和知识产权。
4. **敏感信息**：系统不应做人脸识别或人物画像。若未来增加此类能力，需要按敏感个人信息规则单独评估，不能沿用普通照片上传的告知。
5. **存储与跨境**：需要把 Supabase Storage 实际区域、签名访问、备份、日志和第三方处理者写入数据流台账；如果照片或账户数据从中国大陆传到境外，需专项评估跨境个人信息规则。

### 7.3 上线前最低控制

- 私有 Storage 和短期签名 URL；禁止可猜测的永久公开地址。
- 服务端再次校验 MIME、文件头、大小、数量、对象路径和成员权限，不能只相信前端压缩。
- 继续移除 EXIF 等拍摄元数据，并在隐私政策中如实说明。
- 用户可以删除自己的照片、记录并导出数据；退出或注销后的保留规则与 V1.3 隐私治理 ADR 一致。
- 提供“上传即确认拥有必要权利且不侵犯他人权益”的简短规则入口，但不使用一个笼统勾选代替隐私政策和用户协议。
- 建立管理员隐藏/删除、原因记录、申诉或联系路径；高风险内容可暂停展示。
- 大陆发布前核对 ICP/许可、App 载体、账号认证、公安联网备案、数据跨境和内容治理要求。

## 11. 地点与内容管理：问题和核心决策

### 11.1 当前问题

- 地点进入发现后，普通界面没有地点级管理入口；误标、重复或不应继续展示的地点无法下架。
- 作者已经可以删除自己的到访，Owner/Admin 也已有隐藏到访或照片的底层能力，但当前按钮缺少二次确认、集中列表和恢复路径。
- “去试试”只允许候选创建者编辑或物理删除自己的候选，Owner/Admin 不能处理其他成员留下的错误候选，也无法从管理后台恢复误操作。
- “删除地点”“删除到访”“移除候选”在用户语言中容易混为一谈，但它们对共享数据的后果完全不同。

### 11.2 V1.3.3 的产品决策

V1.3.3 不向任何角色提供地点主数据的物理删除。所有管理动作按对象分开：

| 对象 | 用户可见动作 | 实际行为 | 是否可恢复 |
| --- | --- | --- | --- |
| 已推荐地点 | 下架地点 | 将当前小组的 `group_place` 改为 `archived` | 是 |
| 自己的到访 | 删除这次到访 | 软删除作者自己的 `visit_record` 及关联照片访问 | 用户界面不可恢复；后台按保留规则清理 |
| 他人的到访/照片 | 隐藏内容 | Owner/Admin 治理隐藏，保留原文和审计 | 是 |
| 去试试候选 | 移除候选 | 将 pending 候选软处理为 dismissed，并记录处理类型 | 符合条件时可恢复 |

“下架”是默认地点管理动作，而不是“删除”。原因：

1. `places` 是高德 POI 主数据，可能被多个小组复用，不能因一个小组的操作被删除。
2. `group_places` 被到访、观点、照片、收藏和审计引用，硬删除会触发级联风险。
3. 误操作需要可恢复；历史记录、匿名规则、导出和治理证据也需要保留。
4. 下架只影响当前小组，其他小组对同一 POI 的候选或推荐不受影响。

V1.3.3 不提供永久删除地点、批量清空或绕过保留期的按钮。确需彻底清理的数据，通过受控运维流程另行处理。

## 12. 权限矩阵

| 能力 | Member | Admin | Owner |
| --- | ---: | ---: | ---: |
| 删除自己的到访/照片 | 是 | 是 | 是 |
| 编辑或移除自己创建的 pending 候选 | 是 | 是 | 是 |
| 下架/恢复小组地点 | 否 | 是 | 是 |
| 隐藏/恢复任意成员到访或照片 | 否 | 是 | 是 |
| 移除/恢复他人 pending 候选 | 否 | 是 | 是 |
| 查看内容治理原因和操作时间 | 否 | 是 | 是 |
| 查看其他成员邮箱、管理成员角色与状态 | 否 | 否 | 仅 Owner |
| 物理删除 `places` 或整组历史 | 否 | 否 | 否 |

角色必须由服务端基于当前 active membership 重新判断。前端是否显示按钮不是权限边界；直接调用 RPC 时仍必须拒绝无权限用户。

Admin 的角色说明需更新为：

> Admin 可以管理邀请、地点和小组内容，但不能查看成员邮箱、管理成员角色或导出全组账户资料。

Owner 保留全部内容治理能力和既有成员治理能力。

## 13. 普通页面的快捷管理入口

### 13.1 入口形态

- 发现卡、地点详情和去试试候选卡右上角使用 `···` 管理菜单，不直接暴露垃圾桶。
- 图形按钮的可点击区域不得小于 44 × 44px；视觉图标可保持 18–20px。
- 只有 Owner/Admin 看见地点级管理入口。
- 候选创建者仍可看见自己的“编辑 / 移除候选”，普通成员看不到其他人的管理入口。
- 菜单按钮需要 `aria-label`，例如“管理肯德基（翠桥店）”。

### 13.2 发现卡

Owner/Admin 打开菜单后显示：

1. `查看地点详情`
2. `管理到访记录`
3. `下架地点`

不在卡片上直接显示红色垃圾桶，避免普通浏览时误触和视觉噪音。

### 13.3 地点详情

地点标题区显示 `管理` 菜单：

- `下架地点`
- `管理到访与照片`
- `前往管理后台`

作者自己的到访条目显示 `删除这次到访`；Owner/Admin 对所有条目显示 `隐藏记录`，对照片显示 `隐藏照片`。当操作者同时是作者和管理员时：

- 删除自己的内容使用作者删除逻辑；
- 管理员治理入口单独显示为“作为管理员隐藏”，不能混成一个含义不清的删除按钮。

### 13.4 去试试

- 候选创建者：`编辑候选 / 移除候选`。
- Owner/Admin：可对任何 pending 候选使用 `管理候选 / 移除候选`。
- 已 promoted 候选不能从候选入口回退；应转到正式地点管理并使用“下架地点”。
- 因真实体验选择“这次先不推荐”的 dismissed 候选不在普通列表恢复，避免把真实负向结论变成反复试探；只有受控管理视图可以查看其处理事实。

## 14. “我的”中的地点与内容管理后台

Owner/Admin 在“我的”页面看到新的 `地点与内容管理` 区域。普通 Member 不显示该区域。

### 14.1 总览

顶部显示四个计数：

- 上架中地点
- 已下架地点
- 去试试候选
- 已隐藏内容

计数由服务端管理 RPC 返回，不由客户端读取全表后自行计算。

### 14.2 四个列表

#### 上架中

每行显示：

- 地点名、行政区/商圈、地点类型；
- 当前小碗、有效观点人数、到访记录数、照片数；
- 最近到访日期；
- `查看 / 管理记录 / 下架`。

#### 已下架

每行显示：

- 地点名；
- 下架人可见昵称、下架时间、下架原因；
- 保留的观点、到访和照片数量；
- `查看管理摘要 / 恢复`。

#### 去试试

默认只显示 pending 候选；可切换查看被移除的候选。

- pending：显示创建者昵称、创建时间、来源和期待；
- removed：显示移除类型、操作者、时间和原因；
- 操作：`查看 / 移除 / 恢复`。

#### 已隐藏内容

按时间倒序显示被 Owner/Admin 隐藏的到访和照片：

- 地点、内容类型、作者的治理可见昵称；
- 隐藏人、时间、原因；
- 内容摘要或安全缩略图；
- `恢复显示`。

Admin 不得通过此列表获得其他成员邮箱。匿名记录在普通展示仍显示“匿名成员”；治理列表只显示完成操作所需的最小身份信息。

### 14.3 搜索与分页

- 支持按地点名搜索。
- 支持按状态和内容类型筛选。
- V1.3.3 每次最多返回 50 条，使用“加载更多”，不做复杂无限滚动。
- 管理列表和普通页面使用不同的受控读模型；不能为了开发方便让 archived/hidden 数据重新进入普通查询。

## 15. 二次确认与文案

### 15.1 下架地点

第一层：从管理菜单选择 `下架地点`。

第二层：打开确认对话框：

**标题**

> 下架“{地点名}”？

**后果说明**

> 下架后，这家店会从发现、地图和普通列表中隐藏。已有到访、照片和成员观点会保留，你可以在“我的—地点与内容管理”中恢复。

**必填**

- 下架原因，1–280 字；
- 勾选 `我了解这是对整个小组地点的下架操作`。

只有填写原因并勾选后，`确认下架` 才可用。取消按钮保持普通视觉权重，确认按钮使用危险操作样式。

成功反馈：

> 已下架“{地点名}”。历史内容已保留，可在管理后台恢复。

### 15.2 恢复地点

恢复是可逆操作，但仍需确认：

> 恢复后，这家店会重新出现在发现和地图中，并继续使用原有到访、照片和观点。

如果地点已没有任何有效 current opinion，则恢复为 `inactive_no_marks`，并提示先完成一条真实推荐；不能制造没有推荐依据的发现地点。

### 15.3 删除自己的到访

原来的直接提交按钮改为确认对话框：

> 删除 {日期} 的这次到访？
> 这条感受和关联照片会立即从小组中消失。地点是否继续显示，取决于其他成员和你剩余的有效记录。

确认按钮：`删除这次到访`。

### 15.4 管理员隐藏记录

管理员必须填写 1–280 字原因；确认文案明确：

> 记录会从普通小组视图隐藏，原文不会被改写。可以在管理后台恢复。

按钮：`确认隐藏`。

### 15.5 移除候选

候选创建者确认：

> 从“去试试”移除“{地点名}”？这不会形成公开负面评价。

Owner/Admin 处理他人候选时必须填写原因，并显示：

> 候选会从小组的“去试试”列表隐藏，处理记录会保留。

## 16. 数据模型与 RPC

### 16.1 向前 migration

新增一条 V1.3.3 前向 migration；不修改任何历史 migration。

`group_places` 增加：

- `archived_by uuid null references profiles(id)`
- `archived_reason text null check (char_length <= 280)`

并补强约束：

- `status = archived` 时 `archived_at` 必须存在；
- V1.3.3 新增的下架 RPC 必须同时写入 `archived_by / archived_reason`；
- 非 archived 状态时 `archived_at / archived_by / archived_reason` 均为空；
- 历史 archived 行不得伪造操作者：`archived_by` 可暂时为空，`archived_reason` 回填“历史下架记录未留存原因”；首次恢复后再下架时必须写全三项。

`place_candidates` 增加：

- `resolution_type text null`，受控值建议为：
  - `promoted`
  - `not_recommended`
  - `creator_removed`
  - `manager_removed`
- `resolution_reason text null check (char_length <= 280)`

对历史候选的兼容规则：

- 已 promoted 的候选回填 `resolution_type = promoted`；
- 已 dismissed 且能从既有字段明确判断为真实体验未推荐的，回填 `not_recommended`；
- 其余历史 dismissed 行不伪造创建者或管理员操作，`resolution_type` 保持为空并在管理视图显示“历史处理记录”；
- V1.3.3 上线后的所有 promote/remove 流程必须写入 `resolution_type`，新数据不再允许模糊状态。

沿用 `visit_records` 和 `photos` 已有的：

- `hidden_at`
- `hidden_by`
- `hidden_reason`
- `deleted_at`

### 16.2 地点管理 RPC

新增：

- `archive_group_place(p_group_place_id, p_reason)`
- `restore_group_place(p_group_place_id)`
- `list_group_place_management(p_group_id, p_status, p_query, p_cursor, p_limit)`

要求：

- 必须是该 group 的 active Owner/Admin；
- 使用行锁防止重复下架/恢复；
- 下架只更新当前 `group_places`，不得删除 `places`；
- 写入 audit log；
- 返回前一状态、新状态和需要重新验证的页面路径。

### 16.3 到访删除后的观点重算

扩展 `delete_my_visit_record`：

1. 软删除目标 visit 和关联照片。
2. 查找该用户在同一地点仍未删除的最新 visit snapshot。
3. 有剩余 visit：用最新 snapshot 重建该用户的 `current_opinion`。
4. 无剩余 visit：删除该用户对应的 `current_opinion`。
5. 若地点已没有任何 current opinion，将 `group_places.status` 改为 `inactive_no_marks`；不改为 archived。
6. 若仍有其他成员观点，地点保持 active。
7. 全过程在同一数据库事务中完成并记录 audit。

Owner/Admin 隐藏他人记录不改写其 current opinion，继续遵守 V1.3 隐私治理 ADR 中“管理员不能改写评分或标签”的决定。

### 16.4 内容治理 RPC

沿用并补齐：

- `hide_group_visit_record`
- `hide_group_photo`
- 新增 `restore_group_visit_record`
- 新增 `restore_group_photo`
- 新增 `list_hidden_group_content`

恢复操作只允许 active Owner/Admin，清空 hidden 字段并记录恢复审计，不改变原作者、文字、评分、标签或照片对象。

### 16.5 候选管理 RPC

用软处理替代当前创建者物理删除：

- `remove_place_candidate(p_candidate_id, p_reason default null)`
- `restore_place_candidate(p_candidate_id)`
- `list_managed_place_candidates(...)`

规则：

- 创建者可移除自己的 pending 候选；
- Owner/Admin 可移除任意 pending 候选，且原因必填；
- 移除更新为 dismissed，并设置 `resolution_type`；
- 仅 `creator_removed / manager_removed` 可恢复；
- `not_recommended` 不通过普通恢复操作回到 pending；
- promoted 候选通过正式地点管理，不从候选 RPC 回退；
- 恢复前检查同组不存在 active/inactive 正式地点和另一个 pending 候选。

### 16.6 审计事件

至少记录：

- `group_place.archived`
- `group_place.restored`
- `visit_record.deleted`
- `visit_record.hidden`
- `visit_record.restored`
- `photo.hidden`
- `photo.restored`
- `place_candidate.removed`
- `place_candidate.restored`

metadata 包含适用的：

- previous/new status；
- reason；
- group_place_id/place_id；
- author id；
- 受影响的 visit/photo 数量。

普通产品接口不得返回完整审计 metadata。

## 17. 下架和删除的系统影响

### 17.1 地点下架后

- 从发现列表、地图标记、普通站内搜索和推荐统计入口隐藏。
- 普通成员直接打开详情时显示“这个地点暂时不可用”，不泄露下架原因。
- Owner/Admin 从管理后台仍可查看治理摘要和恢复入口。
- 历史到访、照片、当前观点、收藏和审计记录保留。
- “下回吃”中的收藏不物理删除；普通个人列表显示“已下架”，允许用户移除收藏，但不跳转普通详情。
- 不能再次通过“去试试”创建同一 POI；应提示管理员恢复原地点。

### 17.2 到访删除后

- 立即从地点详情、饭后聊和照片签名访问入口消失。
- 按第 16.3 节重算作者 current opinion。
- 如果最后一份观点被移除，地点进入 `inactive_no_marks`，不会继续显示在发现。
- 照片对象按既有删除与清理策略处理。

### 17.3 管理员隐藏后

- 内容从普通页面立即隐藏。
- current opinion 不被管理员改写。
- 管理后台保留恢复入口和完整审计。

## 20. 权限与数据验收矩阵

### Member

- 能删除自己的到访/照片。
- 能编辑和移除自己的 pending 候选。
- 看不到地点下架、他人内容治理和管理后台入口。
- 直接调用管理 RPC 返回权限错误。

### Admin

- 能下架/恢复当前组地点。
- 能隐藏/恢复组内到访和照片。
- 能处理 pending 候选。
- 不能读取成员邮箱、修改角色或导出全组账户信息。

### Owner

- 具备 Admin 的全部地点与内容管理能力。
- 保留既有成员治理和全组导出能力。
- 同样不能从产品 UI 物理删除 `places` 或绕过审计。

### 数据一致性

- 下架一个组的地点不影响其他组的同一 POI。
- 下架/恢复不丢失到访、照片、观点和收藏。
- 删除最新到访后 current opinion 正确回退到上一条 snapshot。
- 删除最后一条到访后移除该用户 current opinion。
- 全组无观点时地点退出发现。
- 隐藏/恢复不改写原内容。
- 候选移除不物理删除审计事实。
- 所有管理动作存在 actor、时间、原因和对象记录。

产品负责人批准本文件后，状态改为“已批准，待开发”，再按第 18、21、22 节进入编码、测试和发布。若未来要求永久删除地点、管理员改写成员观点或公开负面记录，必须新增 ADR，不能在实现阶段自行扩大权限。
