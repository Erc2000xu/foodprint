# 食迹 Foodprint V1.1.1｜邀请与成员治理开发文档

> 版本：V1.1.1  
> 状态：已开发，待部署与线上验收  
> 建立日期：2026-07-27  
> 前置版本：V1.1（高德地点筛选与导航）

## 1. 背景与目标

V1.1 已上线地点检索与导航能力，但「我的与成员管理」仍存在三个影响实际使用的问题：

1. 邀请原始链接只在生成当次显示；页面刷新或退出后，Owner 无法再次取得仍有效的链接；
2. 已用完、已撤销和已过期邀请持续堆积在管理页面，干扰日常管理；
3. 成员角色已有数据库基础，却没有完整的角色管理、成员目录隐私控制与邮箱识别能力。

V1.1.1 的目标是让邀请可以安全地持续管理，让成员权限可见、可控，并让普通朋友只看到与其使用场景相符的信息。

## 2. 范围与非范围

### 本版本包含

- 仍有效邀请的完整链接展示与一键复制；
- 邀请链接加密保存，不以明文 token 方式落库；
- 管理页仅展示仍可使用的邀请；已用完、已撤销、已过期邀请从日常列表自动隐藏；
- 保存过去 30 天邀请元数据的 Owner/Admin 查询接口，为未来导出入口预留；
- Owner 将成员在 `Admin` 与 `Member` 之间切换；
- Owner 对非 Owner 成员暂停/恢复；
- Owner/Admin 成员目录中显示昵称、邮箱、角色与状态；
- Member 不再读取或看到成员目录；
- 数据库 RLS 与 RPC 同步收紧，不能只依赖前端隐藏。

### 本版本不包含

- Owner 转移、多个 Owner、角色自定义或更细的权限模板；
- 已经生成的历史邀请链接恢复。旧版本只保存 token hash，原始 token 无法也不应从 hash 反推；
- 已邀请记录的后台导出按钮、删除数据库记录或长期审计报表；
- 邮箱 SMTP 的完整配置与邮件模板改版（它属于运行配置，见本项目的认证运维事项）。

## 3. 角色与权限决策

V1.1.1 保持现有三角色，不新增角色。对当前朋友共建型产品而言，三层已经足够；新增角色只会增加理解与误授权成本。

| 能力 | Owner | Admin | Member |
| --- | --- | --- | --- |
| 浏览共同地图、地点、动态和个人记录 | 是 | 是 | 是 |
| 新增真实体验、想去和个人照片 | 是 | 是 | 是 |
| 查看成员目录与邮箱 | 是 | 是 | 否 |
| 创建、复制、撤销邀请 | 是 | 是 | 否 |
| 查看有效邀请与历史元数据接口 | 是 | 是 | 否 |
| 完善历史地点检索信息 | 是 | 是 | 否 |
| 暂停/恢复成员 | 是 | 否 | 否 |
| 切换 Admin / Member 身份 | 是 | 否 | 否 |
| 导出整个共同地图 | 是 | 否 | 否 |
| 更改或移除 Owner | 否（本版本不支持） | 否 | 否 |

`Admin` 是协助 Owner 维护小组的运营角色；`Member` 是被邀请的普通朋友。Member 仍会在地点详情和动态中以昵称出现，因为真实体验需要署名，但不会有「成员名单」入口，也不会取得任何人的邮箱。

## 4. 邀请链接与数据保留规则

### 4.1 有效邀请

仅当邀请未撤销、未过期且 `use_count < max_uses` 时，才在日常「邀请记录」中展示。每条记录显示：

- 完整邀请链接；
- 复制链接按钮；
- 创建时间、有效期、已使用/最大使用次数；
- 撤销按钮。

链接是 bearer credential，拥有链接的人可在有效期内加入共同地图。因此仅 Owner/Admin 可以看到或复制，页面会明确提示不要公开转发。

### 4.2 加密保存

新邀请由服务端生成随机 token；数据库仅保存其 SHA-256 hash 供验证，并保存由服务端环境密钥加密后的 token 密文供 Owner/Admin 重新展示。

- 新环境变量：`INVITATION_TOKEN_ENCRYPTION_KEY`；仅在 Vercel/受控服务端保存，不能以 `NEXT_PUBLIC_` 开头，不能提交到仓库；
- 加密密钥缺失时，系统拒绝生成新邀请，并显示可操作错误；
- 旧邀请没有密文，仍然可以被已有链接使用，但无法重新显示原始链接；Owner 需要创建新邀请替代。

### 4.3 自动隐藏、不是自动删除

已用完、撤销和过期的邀请从日常页面自动隐藏，**不物理删除**。它们仍保留在数据库与审计日志中，便于追溯。

本版本预留 Owner/Admin 的「过去 30 天邀请元数据」查询接口；后续可在不暴露 token 的前提下加入 JSON/CSV 导出按钮。

## 5. 成员数据与隐私规则

- 成员邮箱不复制进公开 `profiles` 表，也不向 Member 返回；
- Owner/Admin 通过受控的 security-definer RPC 读取同组成员的认证邮箱；
- `group_members` 的 RLS 调整为：成员仅可读取自己的 membership；Owner/Admin 才能读取同组完整成员列表；
- Owner 的角色受保护，不能被本版本的角色切换或暂停动作修改；
- 角色与状态变更均写入审计日志。

## 6. 实施项

1. 新建向前兼容的 Supabase migration：加密邀请密文列、有效邀请/30 天历史 RPC、受控成员目录 RPC、RLS 与角色/状态 RPC 加固；
2. 新增服务端邀请 token 加密工具与测试；
3. 更新创建邀请的 Server Action，改为服务端生成/加密 token；
4. 改造邀请列表，只显示有效邀请并提供链接与复制动作；
5. 改造成员管理：Owner 角色切换、暂停/恢复，Owner/Admin 邮箱显示，Member 完全隐藏成员卡片；
6. 更新环境变量模板与 README；
7. 执行 TypeScript、Lint、测试、生产构建与 SQL 结构复核。

## 7. 验收标准

1. Owner 创建邀请后，刷新页面仍可看到同一条完整有效链接并复制；
2. 链接被用完、撤销或过期后，立刻不再出现在日常邀请列表，但数据库历史查询仍可返回元数据；
3. 缺少邀请加密密钥时，不能生成不安全的新邀请；
4. Owner 可将任一非 Owner 活跃成员切换为 Admin 或 Member；Admin 和 Member 均不能改变角色；
5. Owner 可暂停/恢复非 Owner 成员；Admin 和 Member 不能执行该操作；
6. Owner/Admin 能看到成员昵称、邮箱、角色、状态；Member 不会看到成员目录，也不能通过 RLS 查询其他成员；
7. 既有 Owner、地点、邀请验证与数据导出能力不回归。

## 8. 上线顺序与运行配置

1. 在 Supabase Production 执行本版本新增 migration；
2. 在 Vercel Production 与 Preview 设置随机的 `INVITATION_TOKEN_ENCRYPTION_KEY`；
3. 部署应用；
4. 以 Owner、Admin、Member 三个账号分别验收权限；
5. 创建新邀请、刷新后复制、完成一次接受邀请，并检查隐藏/审计行为。

密钥一旦轮换，使用旧密钥加密的仍有效链接将无法重新展示；轮换前应让 Owner 创建新链接并撤销旧链接。
